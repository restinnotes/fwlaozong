## AI科研系统工程建设方案
###### AI Research Operating System · AROS · 技术实施设计书 v0.1
| 项目 | 设计要求 |
| 建设目标 | 建立能够持续积累科学证据、进行理论推理、生成研究假说并接受验证的AI科研系统 |
| 首个应用领域 | 神经科学：STN、DBS、帕金森病冻结步态（FOG） |
| 首个研究任务 | 比较STN神经活动与FOG关系的证据，构建竞争性机制模型 |
| 软件形态 | 本地优先的Web研究工作台，支持模型API |
| 开发策略 | 模块化单体架构，先实现最小科研闭环，再逐步扩展 |
| 第一阶段周期 | 4周，按一名具备Python经验的开发者投入较稳定时间估算 |
| 第一阶段规模 | 40篇核心文献、20项测试任务、单模型推理系统 |
| 最终扩展目标 | 多研究课题、多数据类型、可审计的领域级科研智能体 |
### 01. 总体系统架构
###### 交互层 · Streamlit
###### 项目管理｜文献浏览｜证据审查｜科学问答｜机制分析｜结果导出
###### 科研业务层 · Python Services
###### 文献导入与解析
###### 证据检索与抽取
###### 论断核查与比较
###### 假说生成与批判
###### AI模型层
###### 模型API、结构化输出、提示词版本、调用日志
###### 数据持久化层
###### SQLite、全文索引、原始PDF、证据记录、科研状态
###### 外部资源层
###### Zotero · PubMed · OpenAlex · 用户本地数据
###### 核心架构约束： UI、模型调用、文献解析、数据库操作必须分离；科研记录不能只保存在对话历史中。更换模型时，不需要迁移整个系统。
#### 确定技术栈
| 功能 | 选型 | 依据 |
| 运行环境 | Python 3.12、uv | 依赖管理和可重复部署 |
| 前端 | Streamlit | 快速构建数据和科研交互界面 |
| 数据库 | SQLite + SQLAlchemy | 本地部署、关系型记录、事务支持 |
| 全文搜索 | SQLite FTS5 | 支持文献全文和段落级关键词检索 |
| 文献来源 | Zotero Web API v3、PubMed | 元数据同步与生物医学文献检索 |
| PDF处理 | Docling | 提取结构化文本、表格和页面信息 |
| AI调用 | 官方模型SDK + Pydantic | 将模型输出约束为可检查的数据结构 |
| 计算分析 | pandas、NumPy、SciPy、statsmodels | 表格处理、统计和科学计算 |
| 测试 | pytest + 人工标注基准集 | 自动化功能测试和科研质量检查 |
| 版本控制 | Git + 数据快照 | 代码、配置、科研记录版本管理 |
###### 技术依据：Docling、Zotero API v3、SQLite FTS5、Structured Outputs。这些组件均提供与上述用途对应的功能。

### 03. 数据库设计
###### 数据库不是简单保存论文摘要，而是分别保存文献、原文片段、证据、科学论断和假说。
#### 3.1 核心表结构
| 数据表 | 主要字段 | 作用 |
| projects | id, name, scope, status | 研究项目 |
| papers | id, doi, pmid, zotero_key, title, year, file_hash | 文献身份与去重 |
| source_spans | id, paper_id, page, section, text, locator | 可定位的原文片段 |
| evidence | id, span_id, study_design, variables, result_json, review_status | 研究证据 |
| claims | id, statement, claim_type, status | 科学论断 |
| claim_evidence | claim_id, evidence_id, relation | 论断与支持/反对证据的关系 |
| hypotheses | id, project_id, statement, assumptions, status | 竞争性机制假说 |
| predictions | id, hypothesis_id, observable, condition, falsifier | 预测与可证伪条件 |
| runs | id, model, prompt_version, input_hash, cost, timestamp | AI运行记录 |
| evaluations | id, run_id, task_id, scores_json, reviewer | AEEF及任务评价 |
###### 每张核心表使用稳定ID；外键与唯一约束应在数据库层实现。对主要科研对象记录创建时间、版本和修改历史。
###### 原始PDF和较大中间文件保存在文件系统，数据库保存路径及SHA-256哈希，不把完整PDF直接塞进数据库。
#### 3.2 数据结构示例
##### {
#####   "evidence_id": "EV-0001",
#####   "paper_id": "P-0001",
#####   "source_span_id": "SP-0042",
#####   "question_id": "Q-FOG-001",
#####   "population": "Parkinson's disease",
#####   "intervention": "STN stimulation",
#####   "measurement": "FOG-related outcome",
#####   "reported_result": null,
#####   "effect_estimate": null,
#####   "limitations": [],
#####   "review_status": "pending",
#####   "extraction_model": null
##### }
###### 这是数据结构样例，空值表示尚未提取，不是实际研究结果。更复杂的统计结果可以使用独立的结果表或具有模式校验的JSON字段。
#### 3.3 必须遵守的数据库规则
###### 原文不可被AI覆盖。 AI只能生成独立的结构化提取记录。
###### 每个证据对象必须关联真实的原文片段，不允许以模型记忆代替来源。
###### pending、verified、rejected等审核状态要相互区分。AI不能自动将自己的推断设为verified。
###### 研究假说与已证实事实分开存放。
###### 修改和删除必须保留审计记录，支持恢复历史版本。
### 04. 数据处理与科研推理流程
###### 这是系统最关键的执行部分。每一个步骤都应设计为可单独调用、测试和重跑的Python函数。
###### S01
###### Ingest
###### 导入PDF、DOI和元数据
###### S02
###### Parse
###### 解析章节、段落和表格
###### S03
###### Retrieve
###### 检索与问题相关的原文
###### S04
###### Extract
###### 提取结构化研究证据
###### S05
###### Verify
###### 核查证据及论断支持关系
###### S06
###### Synthesize
###### 比较研究，构建竞争性假说
###### S07
###### Export
###### 生成报告并记录完整运行历史
#### 步骤接口规范
| 步骤 | 建议Python接口 | 主要实现要求 |
| S01 | ingest_paper(source) | DOI规范化、文件哈希、去重、导入日志 |
| S02 | parse_document(paper_id) | 解析章节、表格和页码，保留解析失败记录 |
| S03 | retrieve_evidence(query, filters, top_k) | FTS5全文搜索，按论文、设计、年份筛选 |
| S04 | extract_evidence(span_ids, schema) | LLM按Pydantic模式输出字段，保留空值 |
| S05 | verify_claim(claim_id, evidence_ids) | 自动预审、原文对照、人工确认 |
| S06 | generate_hypotheses(question_id) | 生成机制、预测、替代解释、证伪条件 |
| S07 | export_report(project_id, format) | 输出Markdown、CSV/JSON及引用目录 |
###### 每个接口须定义输入模式、输出模式、异常代码和日志字段；执行失败时不能产生部分标记为成功的科研记录。
###### verify_claim只能生成辅助审查建议，正式确认仍须由研究者执行。结构化输出能够强制模型遵守JSON模式，但不能保证内容在科学意义上真实。
OpenAI API
#### 一次完整科研任务的执行过程
###### 以“解释低频STN-DBS研究结果不一致”为例：
###### 将研究问题拆为研究对象、干预、终点、潜在混杂因素。
###### 搜索相关段落和研究记录，形成候选证据集。
###### 提取刺激频率、脉宽、振幅、电极位置、药物状态、FOG评价方法及结果。
###### 识别研究间的可比性问题；不得将不同设计的结果直接视为同质数据。
###### 构造多个竞争性解释，逐项关联支持与反对证据。
###### 对每个解释生成可观察预测，检查是否具有区分性。
###### 自动检查引用遗漏、 unsupported claims、统计过度解释；待研究者确认后导出。
###### 系统应同时返回“无法判断”的情况，而不是无论如何都给出一个确定机制。

### 07. 验收标准与性能测试
###### 系统不能以“功能按钮可以点击”作为交付标准，必须同时通过软件验收和科研质量验收。
#### 7.1 V0.1验收指标
###### 下表是建议的工程验收阈值，尚不是实测性能。
| 指标 | 初期目标 | 测试方法 |
| 文献导入成功率 | ≥95% | 40篇测试PDF，记录失败原因 |
| 元数据正确率 | ≥98% | 人工核对DOI、题目、年份 |
| 关键段落可定位率 | ≥95% | 100个预标注原文片段 |
| 论断—原文支持精确率 | ≥90% | 人工核对至少100项证据关系 |
| 重要证据检索召回率 | ≥80% | 与人工整理的参考证据集比较 |
| 输出格式合规率 | 100% | JSON Schema及业务规则检查 |
| 严重无依据论断进入已验证库 | 0次 | 审核状态及权限测试 |
| 重复导入造成的重复记录 | 0条 | 幂等性测试 |
| 历史运行可追溯性 | 100% | 检查输入、模型、提示词、证据集版本 |
###### 这里要区分两种准确性：数据符合JSON Schema，不代表科学论断正确；引用确实存在，也不代表引用支持结论。
#### 7.2 科研能力对照实验
###### 设置三种条件：
###### A：直接使用通用模型完成研究任务。
###### B：通用模型加上相同的检索材料，但没有专用科研系统。
###### C：完整的AROS工作流。
###### 三组均使用相同科研问题和预定义评价规则。不同任务使用平衡顺序，避免先后顺序造成偏倚。
###### 主要评价指标：
\[ \text{有效科研任务产出率} =\frac{\text{通过独立审核的任务数}}{\text{全部测试任务数}} \]
###### 同时记录每项任务的人工审查时间、错误严重程度、总运行成本、关键证据遗漏、假说质量和预测可区分性。
###### 只有C显著优于A、B，才可以将额外的系统复杂度解释为有效投入。
###### V0.1采用20项任务主要用于工程试点，不足以完成严格的AEEF专家等级认证。正式认证应增加样本量、独立评审和统计验证。

###### 不建议以“接入更多模型”“使用更多Agent”“储存更多论文”作为独立升级目标。
#### 升级原则
###### 发现检索遗漏，先改检索和证据索引；必要时才加入向量检索。
###### 发现论文理解错误，先检查文档解析、提取模式和原文核对。
###### 发现推理缺陷，先优化分步任务、竞争模型和审查机制。
###### 发现复杂任务执行失败，再考虑独立Agent、工具调用和任务调度。

### 11. 最终技术决策
###### 立即实施
###### Python模块化单体 + Zotero + Docling + SQLite/FTS5 + 单一大模型接口 + Streamlit + pytest。
###### 首个应用
###### STN—FOG文献证据整合及竞争机制假说研究。
###### 第一版成功的定义
###### 不是AI能否自行解决FOG机制，而是系统能否可靠地完成一次从原始文献到可审查科研假说的完整流程，并保留长期可复用的证据与研究记录。
###### 暂缓建设
###### 微调大模型、复杂知识图谱、多Agent框架、自主实验控制、大规模分布式部署。
###### 升级决策依据
###### 与普通AI的实测科研产出质量、人工审查时间、可靠性及系统成本比较。
###### 这份方案已经可以作为第一版软件开发的实施基线。实际开工时，下一层级需要把T01—T12分别细化为开发任务卡，补充每个接口的精确输入输出模式、数据库DDL、测试用例与异常处理规范。
